# 3層アーキテクチャの解説

本プロジェクト（`ir-frontend`）では、システムの保守性や拡張性を高めるために**3層アーキテクチャ**という設計パターンを採用している。
このドキュメントでは、その概念と実装上のルールを解説する。

---

## 1. なぜ3層アーキテクチャを導入するのか？

プログラムを書くとき、画面の表示（UI）、データの計算（ロジック）、APIやデータベースとの通信（データアクセス）をすべて同じ場所に書いてしまうと、以下のような問題が発生する。

- コードが長くなりすぎて読めない（何をしている処理か分かりにくくなる）
- 一部を変更したときに、他の関係ない部分まで壊れてしまう
- 複数人で分担して開発しにくい

そこで、システムを役割ごとに3つの層分割し、お互いの独立性を高めるのが3層アーキテクチャの目的である。

---

## 2. 3つの層の役割

本プロジェクトでは、以下の3つの層に分けてプログラムを記述する。

### (1) プレゼンテーション層 (Presentation Layer) / 画面層
**役割:** ユーザーが見る「画面」を作り、ユーザーからの操作（ボタンクリックなど）を受け取る場所である。
* **主な構成要素:** VaadinのViewクラス、Reactのコンポーネント
* **配置場所:** `presentation/<機能名>/`
* **記述すること:**
  * 画面のレイアウト作成
  * 入力値の受け取りとバリデーション（簡易的な入力チェック）
  * サービス層への処理の依頼
  * サービス層から受け取った結果の画面への表示

### (2) サービス層 (Service Layer) / 業務ロジック層
**役割:** システムの「頭脳」にあたる部分です。アプリケーションが本来やるべき仕事（ビジネスロジック）を実行する。
* **主な構成要素:** Serviceクラス (`〜Service.java`)
* **配置場所:** `service/<機能名>/`
* **記述すること:**
  * プレゼンテーション層から受け取ったデータの加工・集計・計算
  * 複雑な入力チェックや業務ルールの判定
  * 必要なデータを取得・保存するためにデータアクセス層を呼び出す

### (3) データアクセス層 (Repository Layer) / リポジトリ
**役割:** データの保存先（バックエンドのPython APIやデータベース）とやり取りを行う「窓口」である。
* **主な構成要素:** ApiClient (`〜ApiClient.java`), Repository (`〜Repository.java`)
* **配置場所:** `repository/<機能名>/`
* **記述すること:**
  * Python API（FastAPIなど）からのデータ取得・送信（`@HttpExchange` を利用）
  * データベースに対するSQLの実行（`JdbcClient` を利用）

---

## 3. モデル (Model) について

層の間でデータを受け渡しする際には、単なる変数ではなく「データの入れ物」となるクラスやレコード（Record）を使用する。

* **Entity:** データベースから取得したデータをそのまま格納するための入れ物である。（配置場所: `model/entity/<機能名>/`）
* **DTO (Data Transfer Object):** Python APIと通信する際に送受信するJSONデータなどを格納するための入れ物である。（配置場所: `model/dto/<機能名>/`）

---

## 4. 処理の流れの例

ユーザーが「GPAデータを取得するボタン」を押したときの、各層の連携イメージを示す。上から下への一方向にのみ処理を依頼するのがルールである。

1.【Presentation】
ユーザーからのボタンクリックを検知し、「GPAデータの取得」をServiceに依頼する。
2.【Service】
権限の確認や必要なパラメータの準備を行い、「この条件でAPIからデータを取ってきて」とRepositoryに依頼する。
3.【Repository】
Python APIに対して実際にHTTPリクエストを送り、結果（JSON）を受け取ってServiceに返す。
4.【Service】
受け取ったDTOを、画面で表示しやすい形に加工・集計してPresentationに返す。
5.【Presentation】
受け取ったデータをReactのグラフコンポーネントやVaadinの表に渡して、画面に描画する。

このように役割を分担することで、「APIの仕様が変わった」「画面のデザインが変わった」といった変更が発生したときに、修正する範囲を最小限に抑えることができる。
